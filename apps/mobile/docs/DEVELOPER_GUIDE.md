# Assetra One — Mobile Developer Guide

This is the complete developer reference for the Assetra One mobile app: environment setup, how to run and build it, and a troubleshooting runbook for every issue encountered while building this project — with the exact fix for each.

Companion doc: [USER_GUIDE.md](./USER_GUIDE.md) — for end users of the app, not developers.

---

## 1. Tech stack & project structure

| Layer | Technology |
|---|---|
| Framework | Expo SDK 54, React Native 0.81.5, React 19.1 |
| Navigation | `expo-router` (file-based routing) |
| Language | TypeScript |
| State | React Context + `useReducer` (`src/context/AppContext.tsx`), persisted to `AsyncStorage` |
| Auth | `@react-native-google-signin/google-signin` (native Google Sign-In, not a web redirect) |
| Cloud backup | Google Drive REST API (`drive.file` scope), plain `fetch` |
| Local security | 4-digit PIN, SHA-256 hashed (`expo-crypto`), stored in `AsyncStorage` |

This app lives inside an **npm workspaces monorepo** (`assetra-one/`), alongside a web app (`apps/web`). Dependencies are hoisted to the **workspace root** `node_modules` — `apps/mobile` has no local `node_modules` of its own. This single fact is the root cause of most of the trickiest bugs in this project (see §5).

```
assetra-one/                    ← workspace root, node_modules lives HERE
├── apps/
│   ├── mobile/                 ← this app — ALWAYS run commands from here
│   │   ├── src/
│   │   │   ├── app/            expo-router screens (file-based routes)
│   │   │   │   ├── login.tsx
│   │   │   │   └── (app)/      authenticated area
│   │   │   │       ├── _layout.tsx      — app shell: FAB, PIN lock, onboarding, CloudSyncManager
│   │   │   │       ├── (tabs)/          — bottom tab screens (Dashboard, Transactions, Accounts, More)
│   │   │   │       └── *.tsx            — stack-pushed detail screens (Assets, Settings, ...)
│   │   │   ├── components/     shared feature components (modals, PIN screens, etc.)
│   │   │   │   └── ui/         generic UI primitives (Card, Button, AppModal, SelectField, ...)
│   │   │   ├── context/        AppContext.tsx — global state, auth, amount masking
│   │   │   ├── utils/          format, validation, googleAuth, googleDriveSync, dataTransfer, appLock
│   │   │   ├── data/           seed/sample data, category defaults
│   │   │   └── constants/      theme.ts — colors, spacing, fonts (mirrors the web app 1:1)
│   │   ├── android/            native Android project (generated by `expo prebuild` / `expo run:android`)
│   │   ├── app.json             Expo config (package name, permissions, plugins)
│   │   ├── eas.json              EAS Build profiles (development / preview / production)
│   │   └── metro.config.js      monorepo-aware Metro config (watches the workspace root too)
│   └── web/                    separate Vite React web app — same product, different codebase
└── node_modules/               HOISTED dependencies for the whole monorepo
```

**Design intent:** the mobile app mirrors the web app's features, theme, and data model as closely as possible (same colors in `theme.ts`, same reducer action names, same JSON export format), so a backup exported from one app can be imported into the other.

## 2. One-time environment setup (Windows)

You need this once per machine. Skip anything already installed.

### 2.1 Node.js
Node 22+ (confirmed working: `v22.15.0`). Install via [nodejs.org](https://nodejs.org) or `winget install OpenJS.NodeJS`.

### 2.2 JDK 17
React Native 0.81 needs Java 17 specifically (not whatever Android Studio bundles, which may be newer).

```powershell
winget install EclipseAdoptium.Temurin.17.JDK
```

Then set `JAVA_HOME` (persisted, User scope) and add its `bin` to `PATH`:

```powershell
$jdkPath = "C:\Program Files\Eclipse Adoptium\jdk-17.0.19.10-hotspot"   # adjust to your installed version
[Environment]::SetEnvironmentVariable("JAVA_HOME", $jdkPath, "User")
$userPath = [Environment]::GetEnvironmentVariable("Path","User")
[Environment]::SetEnvironmentVariable("Path", "$userPath;$jdkPath\bin", "User")
```

**Open a new terminal after this** — existing terminals won't see the new environment variables.

### 2.3 Android Studio + SDK

```powershell
winget install Google.AndroidStudio
```

Then **launch Android Studio once** and complete the first-run **Setup Wizard** → choose **Standard** install. This downloads the actual Android SDK, platform-tools (`adb`), and an emulator image to `%LOCALAPPDATA%\Android\Sdk`.

Also install, via Android Studio → **SDK Manager → SDK Tools tab** (uncheck "Show Package Details" if the entry doesn't appear):
- ☑ **Android SDK Command-line Tools (latest)** — lets Gradle auto-fetch any missing SDK component instead of failing mid-build.

Then set `ANDROID_HOME` and add `platform-tools` to `PATH`:

```powershell
$sdk = "$env:LOCALAPPDATA\Android\Sdk"
[Environment]::SetEnvironmentVariable("ANDROID_HOME", $sdk, "User")
$userPath = [Environment]::GetEnvironmentVariable("Path","User")
[Environment]::SetEnvironmentVariable("Path", "$userPath;$sdk\platform-tools", "User")
```

**Verify the whole toolchain** (new terminal):
```powershell
java -version      # should print 17.x
adb version        # should print Android Debug Bridge version ...
```

### 2.4 Install project dependencies

⚠️ **Always run `npm install` from the workspace root** (`assetra-one/`), never from `apps/mobile`. This is a monorepo — running it from the wrong directory can install a second, conflicting copy of Expo into the wrong `node_modules` (see [Issue #2](#issue-2-two-expo-versions-installed-app-crashes-or-behaves-oddly) below).

```powershell
cd assetra-one
npm install
```

## 3. Day-to-day development

### 3.1 The mental model: dev build vs. JS changes

A **development build** is a native Android app (a "shell") installed once on your phone or emulator. It contains all your **native** modules (Google Sign-In, Reanimated, etc.) compiled in. Your actual **JavaScript/TypeScript code is NOT baked into it** — instead, the dev build connects live to a **Metro** server running on your PC and loads your JS from there.

This means:
- **Editing screens, styles, logic, adding a new hook/component** → **no rebuild needed.** Just save the file; Metro pushes the update via Fast Refresh in about a second.
- **Adding/removing a native package**, or changing native config in `app.json` (permissions, plugins, icon, splash) → **requires a native rebuild** (`npx expo run:android` again).

If you find yourself waiting minutes for every code change, you are almost certainly rebuilding natively for changes that only needed a JS reload.

### 3.2 Running the dev server

**Always run this from `apps/mobile`, not the workspace root:**

```powershell
cd assetra-one\apps\mobile
npx expo start
```

Wait for `Waiting on http://localhost:8081`. Then open the **already-installed dev-client app** on your phone — it connects automatically if the phone can reach your PC.

**Phone connection — two options:**

**A. USB cable** (simplest, most reliable):
1. Enable **Developer options → USB debugging** on the phone.
2. Plug in the cable, tap **Allow** on the phone's prompt.
3. `adb devices` should list your phone as `device` (not `unauthorized`).
4. Metro's `adb reverse tcp:8081 tcp:8081` is normally run automatically by Expo; if the app can't reach Metro, run it manually:
   ```powershell
   adb reverse tcp:8081 tcp:8081
   ```

**B. Wireless (no cable, same Wi-Fi network)** — two ways:

- **One-time USB, then switch to Wi-Fi** (recommended — most reliable):
  ```powershell
  adb devices                      # confirm phone shows as "device" over USB first
  adb tcpip 5555                   # switches the phone's adb daemon to listen over Wi-Fi
  adb connect <phone-wifi-ip>:5555 # find the IP: adb shell ip route
  ```
  You can now unplug the USB cable — `adb` stays connected over Wi-Fi until the phone reboots or leaves the network.

- **Fully cable-free pairing** (Android 11+, no cable at all): phone → **Developer options → Wireless debugging → Pair device with pairing code** → gives an `IP:PORT` and a 6-digit code (expires in ~2 minutes). Then:
  ```powershell
  adb pair <ip>:<pairing-port> <6-digit-code>
  adb connect <ip>:<connect-port>       # the OTHER port shown, not the pairing one
  ```
  This is fiddlier in practice (codes expire fast, easy to misread the two different ports) — prefer option A above if it fails.

Once connected, `adb reverse tcp:8081 tcp:8081` still needs to be run (over either USB or Wi-Fi `adb`) so the phone can reach Metro on your PC.

**To force-reload the app** without touching your PC: shake the phone → tap **Reload**. Or from the PC, with the app already running:
```powershell
adb shell am force-stop com.vinothdhivik.assetraone
adb shell am start -a android.intent.action.VIEW -d "exp+assetra-one://expo-development-client/?url=http%3A%2F%2Flocalhost%3A8081"
```

## 4. Building

There are three ways to produce an installable app. Pick based on what you need:

| Method | When to use | Time |
|---|---|---|
| `npx expo run:android` | First-time setup, or after adding a native module | ~2–20 min (first time slow, then fast, cached) |
| Local release APK (`gradlew assembleRelease`) | Standalone APK for real-device testing, no Play Store | ~5–20 min |
| EAS cloud build | No local Android toolchain, or need the *exact* Play-Store-signing pipeline | ~15 min – a few hours (free-tier queue) |

### 4.1 Development build (debug)

```powershell
cd apps\mobile
npx expo run:android
```

This regenerates the native `android/` folder (if missing), compiles, installs on the connected device/emulator, and starts Metro. Run this once, then use `npx expo start` for everyday work (§3).

### 4.2 Local release APK (standalone, installable, no Play Store)

```powershell
cd apps\mobile\android
.\gradlew.bat assembleRelease
```

Output: `apps/mobile/android/app/build/outputs/apk/release/app-release.apk`.

**Two monorepo-specific bugs had to be fixed for this to work on Windows** — see [Issue #7](#issue-7-release-build-fails-unable-to-resolve-module-expo-routerentryjs) and [Issue #8](#issue-8-release-build-fails-filename-longer-than-260-characters) below. If you're reading this on a fresh clone, the fixes are already committed in `android/app/build.gradle` — you shouldn't need to touch them again unless something in the toolchain changes.

**Install it directly:**
```powershell
adb install -r apps\mobile\android\app\build\outputs\apk\release\app-release.apk
```

This APK is signed with the **debug keystore** (see `android/app/build.gradle`'s `signingConfigs.release`) — fine for personal testing, **not** what you'd submit to the Play Store (that needs a proper release keystore, see §6).

### 4.3 EAS cloud build

Requires an Expo account (`npx eas-cli login`) and consumes a build credit per run.

```powershell
cd apps\mobile
npx eas-cli build --profile development --platform android   # dev client APK
npx eas-cli build --profile preview --platform android        # standalone APK, for testers
npx eas-cli build --profile production --platform android     # AAB, for Play Store submission
```

Profiles are defined in `eas.json`. Note: the `preview` profile explicitly sets `"android": {"buildType": "apk"}` — without that, EAS defaults to an AAB, which isn't directly installable on a device.

EAS correctly handles this project's monorepo layout without any of the workarounds needed for local builds (§5, Issues #7–8) — it's the more "it just works" option, at the cost of upload time and a queue.

## 5. Troubleshooting runbook

Every one of these was hit and fixed during this project's development. If you see the symptom, jump straight to the fix.

### Issue #1: `Unable to resolve module ../../App` right after project setup
**Symptom:** Metro fails immediately with a resolution error mentioning `expo/AppEntry.js` and `../../App`.
**Cause:** Commands run from the **workspace root** instead of `apps/mobile`.
**Fix:** `cd apps/mobile` before running any `expo`/`npm` command. This is the single most common mistake in this monorepo — check your current directory first whenever something inexplicably breaks.

### Issue #2: Two Expo versions installed — app crashes or behaves oddly
**Symptom:** `npx expo-doctor` reports duplicate `expo`, `react`, `react-native` packages at different versions; native crashes like `NoClassDefFoundError` for classes that "should" exist.
**Cause:** `npm install` was run from the workspace root at some point, which (if a stray `package.json`/lockfile drift occurs) can pull a *different* Expo SDK version into the root `node_modules`, colliding with the version `apps/mobile/package.json` actually declares.
**Fix:**
```powershell
cd assetra-one
rm -rf node_modules package-lock.json apps/mobile/node_modules
npm install
cd apps/mobile
npx expo install --fix
npx expo-doctor          # should report 18/18 (or all) checks passing
```

### Issue #3: `expo-doctor` warns about `metro.config.js` overrides
**Symptom:** doctor flags `watchFolders` / `resolver.disableHierarchicalLookup` mismatches.
**Cause:** An overly defensive `metro.config.js`, often a leftover workaround for Issue #2's duplicate-dependency problem.
**Fix:** Once dependencies are de-duplicated, simplify to Expo's documented monorepo pattern:
```js
const { getDefaultConfig } = require('expo/metro-config');
const path = require('path');
const projectRoot = __dirname;
const workspaceRoot = path.resolve(projectRoot, '../..');
const config = getDefaultConfig(projectRoot);
config.watchFolders = [...new Set([...(config.watchFolders ?? []), workspaceRoot])];
module.exports = config;
```

### Issue #4: App crashes on launch with `NoClassDefFoundError` for an Expo Kotlin class
**Symptom:** e.g. `Failed resolution of: Lexpo/modules/kotlin/views/ComposeViewFunctionDefinitionBuilder` or similar, immediately on launch.
**Cause:** A dependency resolved to an incompatible **canary/nightly** version — npm's semver range resolution can float a `-beta`/`-canary` prerelease tag to a *newer* prerelease than intended (e.g. `~0.2.0-beta.9` resolving to `0.2.0-canary-20260121-xyz`) after a lockfile regeneration. That canary was built against a newer Expo SDK's native core than the app actually has installed.
**Fix:** Find the offending package (check for canary/nightly versions among native `expo-*`/`react-native-*` deps):
```powershell
node -e "const fs=require('fs');/* scan node_modules for canary|nightly|-rc in version strings */"
```
Remove it if unused, or pin it to an exact non-prerelease version in `package.json`, then reinstall and rebuild natively (`npx expo run:android`).

### Issue #5: "There was a problem loading the project" in Expo Go
**Symptom:** Opening the app in the **Expo Go** app shows a generic error, or "This project requires a newer version of Expo Go" / "Project is incompatible."
**Cause:** This app uses **native modules not present in Expo Go** (`@react-native-google-signin/google-signin`, `expo-dev-client`, `expo-glass-effect`). Expo Go can only run pure-JS Expo apps.
**Fix:** Don't use Expo Go for this project. Build and use a **development build** instead (§4.1).

### Issue #6: Xiaomi/Redmi (MIUI/HyperOS) blocks the install with `INSTALL_FAILED_USER_RESTRICTED`
**Symptom:** `adb install`/`expo run:android` fails at the install step with that exact error, even though the build itself succeeded.
**Cause:** MIUI's security layer blocks USB-installed APKs by default.
**Fix:** On the phone: **Settings → Additional settings → Developer options** → enable **"Install via USB"** and **"USB debugging (Security settings)"**. These may require signing into a Mi account with internet access to toggle on. Retry the install afterward.

### Issue #7: Release build fails: `Unable to resolve module ../../node_modules/expo-router/entry.js`
**Symptom:** `gradlew assembleRelease` fails specifically at the `:app:createBundleReleaseJsAndAssets` task (debug builds are unaffected — debug skips embedding a JS bundle entirely, so it never exercises this code path).
**Cause:** This is a genuine bug in how Expo's `export:embed` CLI re-resolves the `--entry-file` argument in an npm-workspaces monorepo, combined with the fact that `expo-router` (and thus its `entry.js`) only exists in the **hoisted workspace-root** `node_modules`, not inside `apps/mobile/node_modules` (which doesn't exist). The React Native Gradle Plugin correctly converts the entry file to a path relative to `apps/mobile` before invoking Expo's CLI — but Expo's CLI then internally re-resolves that relative path against the *workspace root* instead of `apps/mobile`, landing one directory level too high and failing.
**Fix — already applied in `android/app/build.gradle`:**
1. Compute the entry file via Node's own module resolution (robust to hoisting) instead of Expo's fragile `resolveAppEntry` script:
   ```groovy
   def entryFileAbsolute = ["node", "--print", "require.resolve('expo-router/entry.js', { paths: [require.resolve('react-native/package.json')] })"].execute(null, rootDir).text.trim()
   entryFile = file(entryFileAbsolute)
   ```
2. **This alone is not sufficient** — the RN Gradle Plugin still converts it to a relative path before invoking Expo's CLI (see `File.cliPath()` in `@react-native/gradle-plugin`), which is where the actual bug lives. Force an absolute override to win by passing a *duplicate* `--entry-file` flag via `extraPackagerArgs` (CLI arg parsers take the last occurrence of a repeated flag):
   ```groovy
   extraPackagerArgs = ["--entry-file", entryFileAbsolute.replace('\\', '/')]
   ```
If you ever upgrade Expo/React Native and this starts happening again, re-verify with:
```powershell
node --print "require.resolve('expo-router/entry.js', { paths: [require.resolve('react-native/package.json')] })"
```
— confirm it resolves to a real, existing file, and that the fix above is still present in `build.gradle`.

### Issue #8: Release build fails: `ninja: error: ... Filename longer than 260 characters`
**Symptom:** `gradlew assembleRelease` fails during native compilation (`:app:buildCMakeRelWithDebInfo[...]`), specifically referencing an autolinked codegen `.cpp.o` file (e.g. for `react-native-safe-area-context`).
**Cause:** Windows' classic **260-character path limit**. CMake/ninja's autolinked codegen build embeds the *entire absolute source path* into the generated object file's path (to avoid name collisions across modules), so a project nested several directories deep on Windows (e.g. `D:\vinoth_official\dataprow\assetra-one\apps\mobile\android\...`) can push the resulting path over the limit — even with `LongPathsEnabled` set to `1` in the registry, since ninja (bundled with the Android NDK) doesn't itself opt into Windows' long-path APIs.
**Fix — map a short virtual drive letter to the project root, then build from there:**
```powershell
subst X: "d:\vinoth_official\dataprow\assetra-one"     # non-destructive, no files moved
cd X:\apps\mobile\android
.\gradlew.bat assembleRelease
```
This mapping is **session-only** — it does not survive a reboot. Re-run the `subst` command once after restarting your PC, before your next local release build. (`subst X: /D` removes the mapping if you ever need to.)
To make it permanent, add the `subst` command to a startup script, or move the project to a shorter real path (e.g. `D:\assetra-one`) instead — more invasive, but permanent.

### Issue #9: Google Sign-In fails with `DEVELOPER_ERROR`
**Symptom:** Tapping "Sign in with Google" fails immediately with a generic/coded error (native error code 10).
**Cause:** The app's package name + **signing certificate SHA-1 fingerprint** combination isn't registered as an **Android**-type OAuth client in Google Cloud Console. Every distinct build (debug keystore, EAS-managed keystore, your eventual Play Store upload key) has its own SHA-1 and needs its own Android OAuth client entry — but they all share the *same* Web-type client ID in code.
**Fix:**
1. Get the SHA-1 of whichever keystore signed the build that's failing:
   ```powershell
   keytool -list -v -keystore apps\mobile\android\app\debug.keystore -alias androiddebugkey -storepass android -keypass android
   ```
   (For an EAS-managed keystore: `eas credentials`.)
2. In [Google Cloud Console → Credentials](https://console.cloud.google.com/apis/credentials), **Create Credentials → OAuth client ID → Android**, using this project's package name (`com.vinothdhivik.assetraone`) and the SHA-1 from step 1.
3. Wait a few minutes for propagation, then retry. **Do not** put this Android client's ID anywhere in the app's code — only the separate **Web**-type client ID (in `.env` as `EXPO_PUBLIC_GOOGLE_CLIENT_ID`) is ever referenced by `GoogleSignin.configure({ webClientId: ... })`. The Android client's existence alone is what Google checks against the app's signature.

### Issue #10: Google Drive sync fails with `AUTH_EXPIRED`
**Symptom:** Manual "Sync Now" or the silent background auto-sync fails, sometimes surfacing a raw `AUTH_EXPIRED` message or a dev-mode error overlay.
**Cause:** The Drive OAuth **access token** expires after roughly an hour. The original implementation just failed and asked the user to disconnect/reconnect — even though the underlying Google session was still perfectly valid and a fresh token was available for free.
**Fix — already implemented in `src/utils/googleDriveSync.ts`:** every Drive request goes through a shared `authorizedFetch()` helper that, on a `401`, silently calls `GoogleSignin.getTokens()` again (the native SDK refreshes under the hood, no user interaction) and retries the request once before giving up. Only a *second* failure surfaces the "please reconnect" message.

### Issue #11: Drive upload fails / silently does nothing (before the fix above existed)
**Symptom:** `uploadToDrive` errors or the multipart request behaves unexpectedly.
**Cause:** The original implementation built the multipart body using `Blob`/`FormData`, which **React Native's `fetch` does not support** for multipart uploads (this is a browser API assumption that doesn't hold on native).
**Fix:** Build the `multipart/related` body as a plain string with an explicit boundary, and set `Content-Type: multipart/related; boundary=...` manually (see `uploadToDrive` in `googleDriveSync.ts`).

### Issue #12: Form modals — the Save/Cancel buttons are unreachable behind the keyboard
**Symptom:** Opening a keyboard while a form (Add/Edit anything) is open pushes content around such that the submit button is invisible or unreachable; on some attempts the entire form seemed to only show a floating button, cutting off the input fields.
**Cause:** Several iterations were tried — `KeyboardAvoidingView` with manual padding math (broke on edge-to-edge display), then a custom `Keyboard` event listener computing padding manually (also broke, pushing the whole sheet off-screen when the computed keyboard height was miscounted with the translucent status bar).
**Fix — the version that actually works, in `src/components/ui/AppModal.tsx`:**
- A bottom-sheet layout: `Modal` → `KeyboardAvoidingView behavior={Platform.OS === 'ios' ? 'padding' : 'height'}` → a `View` capped at `maxHeight: '85%'` containing a fixed header, a scrollable body (`ScrollView`, no manual flex tricks), and a **fixed footer** (`Save`/`Cancel` passed via an explicit `footer` prop, rendered *outside* the scrollable area so it's always visible above the keyboard).
- Every Add/Edit form in the app passes its action buttons via this `footer` prop — if you add a new form, follow the same pattern rather than putting buttons inside the scrollable children.

### Issue #13: Dropdown (`SelectField`) opens as an awkward bottom sheet instead of a clean picker
**Fix:** Changed its `Modal` overlay from `justifyContent: 'flex-end'` (slide-up sheet) to `justifyContent: 'center'` with `maxHeight: '80%'` — a simple centered, scrollable picker.

### Issue #14: Tab bar and floating "+" button overlap the phone's gesture/home bar
**Cause:** Fixed pixel heights (`height: 64`, `paddingBottom: 10`) don't account for the device's bottom safe-area inset (the gesture navigation bar).
**Fix:** Use `useSafeAreaInsets()` and add `insets.bottom` to the tab bar's height/padding, and to the FAB's `bottom` offset (with an extra `raised` amount when a tab bar is also present on-screen — see `src/components/ui/FAB.tsx` and `src/app/(app)/(tabs)/_layout.tsx`).

### Issue #15: The eye-toggle (hide/show amounts) only updated some amounts on screen
**Cause:** `React.FlatList` doesn't re-render its rows just because some *external* state changed — it needs an explicit signal.
**Fix:** Pass `extraData={amountsHidden}` to every `FlatList` that renders formatted amounts, so a masking toggle forces all visible rows to re-render. Also ensure `fmt`/`fmtSigned`/`fmtN` are pulled from `useApp()` (closures over React state, always fresh) rather than a module-level mutable flag (which is fragile — Metro's Fast Refresh and multiple import sites can desync a plain module-scope variable from what's actually re-rendered).

### Issue #16: Signing in with Google immediately asks for the PIN too
**Cause:** The PIN-lock effect fired on *every* transition of `currentUser` from `null` to a value — including the very moment of an interactive sign-in, not just when a session was *resumed* from storage on a cold start.
**Fix:** `AppContext` exposes a `justSignedIn` flag, set to `true` only inside `loginWithGoogle()` (the interactive path). The app shell's lock effect checks and consumes this flag once: if set, it skips the PIN check for that one transition; any *other* time `currentUser` becomes truthy (i.e., a resumed session on cold start, or returning from the background) still locks normally.

### Issue #17: Forgot your PIN — no way back in
**Cause:** The original PIN-lock screen was a dead end with no escape hatch.
**Fix:** A "Forgot PIN?" link on the lock screen clears the stored PIN and signs the user out (`clearPin()` + `logout()`), returning them to the Google sign-in screen. They sign in again and set a fresh PIN from Settings. This is the only "reset" mechanism possible without a backend.

### Issue #18: `expo-doctor` / dependency drift after any fresh `npm install`
**General rule:** after *any* dependency change in this monorepo, run, in order:
```powershell
cd apps/mobile
npx expo install --fix
npx expo-doctor
```
Fix anything doctor reports before assuming a build failure is something else — dependency mismatches are the single most common root cause of confusing native build/runtime errors in this project.

## 6. Publishing to the Play Store (not yet done — reference only)

Not completed as of this writing, but the path is:
1. Create a **Google Play Developer account** ($25 one-time).
2. Build a **production AAB**: `eas build --profile production --platform android` (uses EAS-managed signing — Google Play App Signing).
3. Register that build's SHA-1 (`eas credentials`) as **another** Android OAuth client in Google Cloud Console (see Issue #9 — the production signing key is different from your debug/EAS-preview keys, so it needs its own entry).
4. `eas submit --platform android` to upload the AAB to the Play Console, or upload manually via the Play Console UI.
5. Complete the Play Console's store listing, content rating, privacy policy URL, and data-safety form before it can go out for review.
